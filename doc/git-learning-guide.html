AI 时代，Git 学到什么程度？

不是学多少的问题，而是 学哪些 的问题

Git 是一个庞然大物——光 git help -a 就能列出 150+ 条命令。在 AI 时代，你不需要掌握所有命令，但有一个东西 AI 给不了你：对仓库当前状态的正确心智画像。当 AI 建议你 git reset --hard 时，你得自己判断这会不会丢数据——AI 不会为你的代码负责。

下面按重要程度分四层，逐层拆解你需要学到什么程度，以及为什么。

第一层 必须懂

这一层的知识在你的大脑里，不在 AI 的 token 里。你每敲一次 Git 命令，都在依赖它们。

1.1 分支不是目录，是一个 41 字节的文本文件

很多人以为"切分支"是把文件内容换成了另一个版本。实际上，分支只是一个指向 commit 的指针——它就是一个文本文件，里面只有 40 个字符的 SHA-1 哈希 + 一个换行符。

# 看看分支"长什么样" $ cat .git/refs/heads/main a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0 # 就这一行。没有别的。 # 创建分支 = 写一个 41 字节的文件 $ git branch feature-x → 等同于 echo "a1b2..." > .git/refs/heads/feature-x # 删除分支 = 删掉这个文件 $ git branch -d feature-x → 等同于 rm .git/refs/heads/feature-x → commit 数据不会丢失（只要还有其他引用指向它）
这意味着什么？

创建分支是 瞬时 的——它不是拷贝整个工作目录，只是写一个 41 字节的文件。这就是为什么 Git 的分支如此廉价，你可以随便创建和删除。

多个分支可以指向同一个 commit：

# 三个分支，指向同一个 commit $ git log --oneline -1 a1b2c3 (HEAD -> main, feature-a, feature-b) Initial commit # 此时三个分支完全等价——它们只是三个不同的指针，指着同一个地方 # 之后谁往前走，谁就和新 commit 绑定

指针移动的物理含义

# 初始状态 A ── B ── C ← main ← HEAD # git commit → 新 commit D，main 指针前移 A ── B ── C ── D ← main ← HEAD # git reset --hard HEAD~1 → main 指针回退到 C A ── B ── C ← main ← HEAD \ D ← 还在对象库里，但没有引用指向它了（"悬空对象"）

1.2 历史是有向无环图（DAG），不是一条直线

每个 commit 都记录了至少一个 parent（除了最初的 commit）。合并 commit 有两个 parent。这就构成了一个有向无环图（DAG）。

# 查看 commit 的 parent $ git cat-file -p HEAD tree d4e5f6... parent b7890a... ← 这个 commit 的 parent author Alice <alice@example.com> 1713456789 +0800 committer Alice <alice@example.com> 1713456789 +0800 Fix login timeout bug
# 朴素认知：Git 历史是一条直线 A → B → C → D # 真实情况：Git 历史是一个 DAG（有向无环图） A ── B ── C ── D (main) \ E ── F (feature-A) \ G ── H (feature-B 从 feature-A 分出来) # 合并后 A ── B ── C ── D ── M (main) \ / E ── F ── G ── H ↑ M 有两个 parent：D 和 H

为什么要理解这一点？因为很多命令的行为取决于 parent 链：

# git log main..feature # = "在 feature 上但不在 main 上的 commit" # = 从 feature 出发，沿 parent 链往回走，排除 main 可达的 # git merge-base main feature # = "main 和 feature 的共同祖先" # = DAG 中两条路径交汇的那个 commit（图中的 B） # git branch --merged main # = "所有其 tip commit 是 main 的祖先的分支" # = 从 main 沿 parent 往回走，看哪些分支包含在这条路径上
为什么叫"有向无环图"？

有向：parent 关系有方向——commit 指向它的 parent，反过来不行。子 commit 知道父 commit 是谁，父 commit 不知道子 commit 是谁。

无环：不能出现循环——一个 commit 不能间接成为自己的祖先。这保证了历史总是可以"从任何 commit 走到根"，而不会陷入死循环。

1.3 暂存区是工作目录和 HEAD 之间的缓冲区

Git 的文件有三个"居所"：工作目录、暂存区（index）、HEAD 指向的 commit。每个地方的文件内容可以不同。

工作目录 暂存区 (index) HEAD ┌─────────────────┐ ┌──────────────────┐ ┌─────────────────┐ │ main.c (v4) │ │ main.c (v3) │ │ main.c (v2) │ │ lib.c (v3) │ │ lib.c (v2) │ │ lib.c (v1) │ │ new.py (新) │ │ new.py (新) │ │ (没有这个文件) │ │ README (v1) │ │ (没加进去) │ │ README (v1) │ └────────┬────────┘ └────────┬─────────┘ └────────┬────────┘ │ │ │ ▼ ▼ ▼ git add 写入 git commit 写入 已提交的快照 "改了但没加" "加了但没提交" "已保存"

一个文件同时有三个版本在系统中

# 场景：你在改 main.c $ echo "line 1" > main.c # 初始内容，git add && git commit $ echo "line 2" >> main.c # 继续改，还没 add # 此时 main.c 的三个版本： 工作目录: "line 1\nline 2\n" ← 硬盘上的实际内容 暂存区: "line 1\n" ← 上次 git add 的版本 HEAD: "line 1\n" ← 上次 commit 的版本 $ git add main.c # 现在暂存区更新了： 工作目录: "line 1\nline 2\n" 暂存区: "line 1\nline 2\n" ← 更新了 HEAD: "line 1\n" $ git commit -m "add line 2" # commit 后： 工作目录: "line 1\nline 2\n" 暂存区: "line 1\nline 2\n" HEAD: "line 1\nline 2\n" ← 三者同步了

暂存区的精妙之处

暂存区让你可以部分提交——一个文件改了 10 行，可以先只提交 3 行，剩下的 7 行下次再提交：

# 只暂存文件的一部分修改 $ git add -p main.c ← 交互式选择哪些改动加入暂存区 Git 会显示每个代码块（hunk），让你逐块确认： @@ -10,3 +10,10 @@ context line +added line 1 +added line 2 ← 选 y: 这几行加入暂存区 context line +added line 3 +added line 4 ← 选 n: 这几行留在工作目录，下次再说 # 结果：一次修改拆成两次精致的小提交

1.4 HEAD、refs、remotes 之间的连线

# 在 main 分支上，本地和远程各有一个 commit HEAD ──符号链接──▶ refs/heads/main ──指向──▶ commit abc123 (你的最新本地 commit) refs/remotes/origin/main ──指向──▶ commit def456 (上次 fetch/push 时远程的样子) # 如果 abc123 ≠ def456，说明本地和远程分叉了
# 分离头指针（detached HEAD） $ git checkout a1b2c3 HEAD ──直接指向──▶ commit a1b2c3 ← 不在任何分支上！ # 此时如果你 git commit： HEAD ──直接指向──▶ commit a1b2c3 ──parent──▶ commit xyz789 (新 commit) ↑ 没有分支指向它 ↑ 这个新 commit 也没有分支指向它 # 如果你现在切回 main 分支： # 新 commit xyz789 变成"悬空对象"——没有引用指向它 # 除非你用 reflog 找回（后面会讲）
常见误解

误解："git fetch 会把远程的改动拉到本地工作目录。"

真相：git fetch 只更新 refs/remotes/origin/*——它只下载远程对象并移动远程跟踪分支的指针，不碰你的工作目录和本地分支。

# fetch 前后对比 # fetch 前： refs/remotes/origin/main → abc123 refs/heads/main → abc123 ← 同步 # 同事 push 了一个新 commit xyz789 到远程 # git fetch 后： refs/remotes/origin/main → xyz789 ← 更新了 refs/heads/main → abc123 ← 没动! # 此时 git status 会显示 "Your branch is behind 'origin/main' by 1 commit" # 想把这些改动合并进来？用 git merge 或 git rebase

1.5 对象模型：Git 存储的四个"积木"

Git 底层只有四种对象类型。所有高级命令（branch、merge、rebase）都是这四个积木的排列组合：

📄

Blob — 文件内容

只存内容，不存文件名。相同内容的文件只存一份（相同 SHA-1）。文件名由 tree 对象记录。

📁

Tree — 目录快照

记录文件名、权限、以及对应 blob（或子 tree）的 SHA-1。这就是"某个时刻的目录结构"。

📝

Commit — 一次提交

指向一个 tree（根目录快照）、记录 parent、作者、时间、提交信息。历史就是 commit 组成的链表/图。

🏷️

Tag — 带注释的标签

指向一个 commit（或任意对象），可以 GPG 签名。v1.0.0 这种里程碑就是 tag。

# 一个 commit 里发生了什么——完整拆解 $ git cat-file -p HEAD tree 29ff16c9c14e2652b4f4b8a1b4c1f7c5c7a5d3e1 parent 5b10d2c5d4e3f2a1b6c7d8e9f0a1b2c3d4e5f6 author zefy <zefy@example.com> 1713456789 +0800 committer zefy <zefy@example.com> 1713456789 +0800 Fix login timeout $ git cat-file -p 29ff16 # 展开 tree 对象 100644 blob e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 .gitignore 100644 blob 7c23e78a3b6c4d5e6f7a8b9c0d1e2f3a4b5c6d7e README.md 040000 tree a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2 src # 文件内容存在 blob 里 $ git cat-file -p e69de2 # .gitignore 的 blob node_modules/ dist/ # src/ 是一个子 tree $ git cat-file -p a3b4c5 # src/ 目录的 tree 100644 blob b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1 index.ts 100644 blob c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2 utils.ts # 结构关系： # commit → root tree → {.gitignore blob, README blob, src tree → {index.ts blob, utils.ts blob}}
关键推论

如果两个 commit 之间有 1000 个文件，但你只改了 1 个——那 999 个文件的 blob 和 tree 完全复用，新的 commit 只指向新的 tree（而这个 tree 的其余条目指向的 blob 和上一个版本完全相同）。这就是 Git 不会为每个版本存储完整项目拷贝的原因。

第二层 应该会

这一层是决策层。AI 能帮你执行命令，但选哪个策略、评估什么后果，是你的判断。

2.1 Rebase vs Merge：一个决策，两个世界

🔀

Merge（合并）

做什么：创建一个新的 merge commit，把两个分支的 head 连起来。

效果：保留完整的开发轨迹——能看到 feature 分支是从哪分出来的、中间做了什么、最后在哪合回去。

历史：带分叉的 DAG，真实但可能很乱。

适合：公共分支（main/develop）、多人协作、需要审计的仓库。

危险：频繁合并会让历史变成"意大利面条"。

📏

Rebase（变基）

做什么：把 feature 分支的 commit "搬"到 main 的最新 commit 上，重写每个 commit。

效果：历史变成一条干净的直线——看起来像是先有了 main 的最新代码，再基于此开发了 feature。

历史：线性干净，但失去了"feature 是何时分出来的"这个信息。

适合：私有 feature 分支、推到远程之前整理 commit。

危险：改变了 commit 的 SHA-1——如果这些 commit 已经被别人 pull 了，会造成混乱。

# Merge 流程 A ── B ── C ── D (main) A ── B ── C ── D ── M (main) \ ──merge──▶ \ / E ── F (feature) E ── F ────┘ ↑ M 是 merge commit，parent 是 D 和 F # Rebase 流程 A ── B ── C ── D (main) A ── B ── C ── D ── E' ── F' (feature) \ ──rebase──▶ ↑ 注意：E' 和 F' 是全新的 commit！ E ── F (feature) SHA-1 和原来的 E、F 完全不同
Rebase 黄金法则

永远不要 rebase 已经 push 到公共仓库的 commit。

原因：rebase 会产生新的 SHA-1。如果你的同事已经基于你原来的 commit（旧 SHA-1）做了开发，你 force push 新的 SHA-1 后，同事的本地仓库会出现"同一个改动有两份不同 SHA-1 的 commit"这种混乱。修复这种混乱比 merge 的意大利面条难得多。

什么时候用什么？——决策流程图

# 判断逻辑 你的分支 push 到远程了吗？ ├── 没有 → 随便 rebase（没有别人依赖它） │ └── 推了，但这是你自己的 feature 分支，确定只有你一个人在用？ ├── 是 → 可以 rebase + force push（但要和团队约定好） │ └── 不是 / 不确定 → 用 merge，不要 rebase # 团队经验法则： # main / develop → 永远 merge # feature / fix → rebase 到 main 再提 PR（保持 PR history 干净） # 代码审查后 → squash merge 或 rebase merge 到 main（看团队偏好）

2.2 Reflog：你的"后悔药"

每一次 HEAD 移动，Git 都会悄悄记下来。这就是 reflog。

# 窥探 reflog $ git reflog a1b2c3d HEAD@{0}: commit: Fix login timeout d4e5f6a HEAD@{1}: reset: moving to HEAD~1 ← 你刚 reset 掉的 commit b7890a1 HEAD@{2}: commit: Add user profile page c3456d7 HEAD@{3}: checkout: moving from feature to main e8901b2 HEAD@{4}: commit: Refactor auth middleware # 每一个 HEAD@{n} 都可以 checkout 回去！ $ git checkout HEAD@{2} # 回到"Add user profile page"那一刻

实战：用 reflog 挽救丢失的 commit

# 场景：你不小心 git reset --hard，丢了 3 个 commit $ git reset --hard HEAD~3 HEAD is now at d4e5f6a ← 啊！前面 3 个 commit 不见了！ # 别慌——reflog 记录了一切 $ git reflog d4e5f6a HEAD@{0}: reset: moving to HEAD~3 a1b2c3d HEAD@{1}: commit: Fix login timeout ← 就是这个！ b7890a1 HEAD@{2}: commit: Add user profile c3456d7 HEAD@{3}: commit: Update dependencies # 回到 HEAD@{1}，也就是丢失前的状态 $ git reset --hard HEAD@{1} HEAD is now at a1b2c3d ← 恢复了！三个 commit 都回来了
# 场景：错误的 rebase 后恢复 $ git rebase main # 一堆冲突，解决了一部分，但最终发现 rebase 方向搞反了…… # 想回到 rebase 之前？ $ git reflog abc1234 HEAD@{0}: rebase (finish): ... def5678 HEAD@{1}: rebase (start): checkout main feedbac HEAD@{2}: commit: My feature work ← rebase 前的最后一个 commit $ git reset --hard HEAD@{2} # 完美回到 rebase 前。rebase 产生的 commit 和冲突修改全部丢弃。
Reflog 的时限

Reflog 条目默认保留 90 天（不可达条目）或永久（可达条目）。只要在 90 天之内，你几乎总能找回"丢失"的 commit。过了 90 天，git gc 会清理掉它们。

2.3 合并冲突：不是 Bug，是 Git 在说"你来裁决"

冲突发生时，Git 的信息很清楚：两个分支在同一个文件的相同位置，做了不同的改动。我不知道哪个对，你来决定。

三路合并的本质

# 三路合并的三个输入 Base（共同祖先） function login() { return "ok"; } ↙ ↘ Ours（你的版本） Theirs（对方的版本） function login() { function login() { validateInput(); auditLog(); return "ok"; return "ok"; } } # 合并算法对每一行做判断： # Base 有 "return ok" → Ours 没改 → 没冲突 # Ours 新增 validateInput() → Theirs 也在这个位置新增了 auditLog() → 冲突! # Git 不知道谁先谁后、哪个对，所以标记冲突让你裁决 # 融合后（你手动裁决的结果）： function login() { auditLog(); validateInput(); return "ok"; }

冲突标记的含义

<<<<<<< HEAD ← 你的当前分支的版本 function login() { validateInput(); ← 你加的这一行 return "ok"; } ======= ← 分隔线 function login() { auditLog(); ← 对方加的这一行 return "ok"; } >>>>>>> feature-branch ← 你要合并进来的分支版本

索引中的三阶段（stage）条目

冲突时，同一个文件在暂存区里有三个条目，通过 stage 编号区分：

# 查看冲突文件的 index 条目 $ git ls-files -s conflict.c 100644 d4e5f6a7 1 conflict.c ← stage 1: 共同祖先（base） 100644 b8c9d0e1 2 conflict.c ← stage 2: 你的版本（ours） 100644 f2a3b4c5 3 conflict.c ← stage 3: 对方的版本（theirs） # 查看某个版本的完整内容 $ git show :1:conflict.c # 看共同祖先的版本 $ git show :2:conflict.c # 看你的版本 $ git show :3:conflict.c # 看对方的版本 # 解决冲突后，staged 条目合并为一个 stage 0 $ git add conflict.c $ git ls-files -s conflict.c 100644 e7f8a9b0 0 conflict.c ← stage 0: 已解决，待提交
冲突时你有哪些选择
  • git checkout --ours conflict.c — 完全采纳自己的版本
  • git checkout --theirs conflict.c — 完全采纳对方的版本
  • git mergetool — 用可视化工具（VSCode/vimdiff/Beyond Compare）三栏对比着解决
  • 用 AI 建议合并 — 把冲突文件和两边内容给 AI，让它建议融合方案（但要审查）
  • git merge --abort — 放弃合并，回到合并前

2.4 提交信息不是写给今天，是写给两年后的自己

一个好的 commit message 在两年后、你完全忘记了这段代码时，仍能让你理解"为什么这么改"。AI 可以根据 diff 写摘要，但 "为什么"只有你知道。

推荐格式：约定式提交（Conventional Commits）

# 好的 commit feat(auth): add OAuth2 login flow Replace the old session-based auth with OAuth2 PKCE flow. The old approach broke on Safari due to third-party cookie blocking (ITP). PKCE avoids cookies entirely. Closes #342 # 坏的 commit——两年后没人知道为什么 fix login
feat:新功能
fix:修 bug
refactor:重构（不改变行为）
docs:文档
test:测试
chore:杂务（构建、依赖）

2.5 常用救援操作速查

⏪

撤销还没 push 的 commit

git reset HEAD~1 — 撤销最近一次 commit，改动回到工作目录

git reset --soft HEAD~1 — 撤销 commit 但改动保留在暂存区

🔙

撤销某个文件到某次 commit

git checkout a1b2c3 -- file.txt — 把 file.txt 恢复到 commit a1b2c3 时的样子

🧹

已经 push 了，要撤销

git revert HEAD — 创建一个新 commit，内容是"撤销上一个 commit 的改动"

这个是安全的——不重写历史，只加新记录。

📌

暂存当前改动

git stash — 把所有未提交的改动暂存起来，工作目录变干净

git stash pop — 还原最近一次 stash 的改动

git stash list — 查看所有 stash 条目

🔍

找出谁改了什么

git blame file.txt — 每一行是谁、哪次 commit 改的

git bisect — 二分法查找 bug 是在哪次 commit 引入的

📝

修改最后一次 commit

git commit --amend — 修改上次 commit 的信息或追加文件

注意：这也会产生新的 SHA-1。如果上次 commit 已经 push 了，不要 amend。

第三层 交给 AI

这一层的特点是：机械、模式化、后果可控、错了也容易回滚。最适合 AI 来做。

⌨️

拼命令参数

"帮我看最近 20 条 commit，带分支图" → git log --oneline --graph --decorate -20

"把 feature 分支 rebase 到 main 上" → git rebase main（但决定 rebase 还是 merge 要靠你）

✍️

写 commit message

把 git diff --staged 的输出丢给 AI，让它生成约定式提交格式的信息。你再补充"为什么"。

🛡️

生成 .gitignore

"给我生成一份 Python 项目的 .gitignore" → AI 生成包含 __pycache__/ .venv/ *.pyc 等的完整规则。

🔀

解决简单合并冲突

两个分支各加了一个不冲突的 import → AI 可以自动合并。复杂逻辑冲突仍需人工审查。

🧹

批量清理分支

"把已合并到 main 的本地分支全删掉" → AI 生成 git branch --merged main | grep -v main | xargs git branch -d

🔎

操作历史查询

"这个 bug 哪次 commit 引入的？帮我定位" → AI 引导你使用 git bisect

第四层 不必深究

知道它们存在即可。需要时知道去哪查。真正的价值在于理解"Git 为什么快、为什么不会撒谎"。

可以不知道细节的东西
  • packfile 的二进制格式和增量压缩算法细节
  • pkt-line 传输协议和 multi_ack 协商
  • index 文件的字节级布局
  • SHA-1 → SHA-256 的迁移方案
  • Git 内部 C 源码的具体实现

除非你在做 Git 工具链、CI 系统集成、或者想给 Git 贡献代码——否则这些不需要装入大脑。

一句话总结

知道状态机长什么样，但不一定要会手写所有状态转换的汇编

每次 HEAD 移动都有记录，出了事能找到回家的路。git reflog + hash = 万能后悔药。

🔑

暂存区当缓冲区

理解 add → commit 的两步节奏。能用 git add -p 精细拆分提交。

🔑

Rebase 当编辑器

在 push 前可以尽情改写历史。一旦 push 到公共仓库，就把 --force 从肌肉记忆里删掉。

🔑

AI 当副驾驶

让它拼命令、写信息、解简单冲突。但什么时候该让 AI 停下——那是你决定的。

记住 git rebase --onto 的参数顺序不值钱。
知道为什么不该对公共分支 --force，才值钱。
